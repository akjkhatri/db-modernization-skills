# .dbmod memory specification (v1.0)

This is the contract shared by all three skills. Scripts enforce most of it, and `memory_validate.py` checks it.

## 1. Layout
```
<app-repo>/
  .dbmod/
    manifest.json               phase, counters, context registry
    standards.json              target design standards (human-owned)
    README.md, changelog.md     human-readable
    journal.jsonl               append-only machine run log
    legacy/
      sources/                  copies of every catalog export ingested (+ sha256 in manifest)
      catalog.json              canonical legacy model (regenerated by ingest, never hand-edited)
      relationships.json        declared + inferred relationships with review status
      findings.json             assessment findings, table health scores, PII inventory
      domains.json              legacy domain clusters (candidate -> confirmed)
      glossary.json             legacy abbreviations -> expansions (suggested / confirmed / unknown)
      sme_questions.json        questions for the business, with answers and who gave them (business gate)
      assessment/report.md      assessment report (narrative + generated sections)
      assessment/erd/*.md       Mermaid ERDs per legacy domain
    target/contexts/<ctx>/
      model.json                CURRENT target model of the bounded context (working copy)
      design.md                 design notes: aggregates, invariants, legacy rationale
      snapshots/vNNN.json       immutable copy of each ACCEPTED model version
      pending/                  preview migrations not yet accepted
    mapping/<ctx>.json          lineage for one context (one file per context = fewer merge conflicts)
    requirements/index.json + REQ-nnnn-*.md
    decisions/index.json + ADR-nnnn-*.md
  db/migration/                 Flyway migrations (location set in standards.json)
  db/data-migration/<ctx>/      one-off legacy -> new ETL scripts and reconciliation queries
```

## 2. Lifecycles
| Object | States | Who moves it |
|---|---|---|
| Phase (manifest) | initialised → ingested → assessed → modernizing | scripts |
| Legacy domain | candidate → confirmed (or merged/split) | human confirms; Claude proposes |
| Relationship | inferred → confirmed / rejected (declared ones are always confirmed) | human, via Claude |
| Finding | open → accepted-risk / resolved-in-target / not-applicable; `not-detected` when re-analysis no longer finds it (id kept) | Claude, with justification (`review.py`, `memory_record.py finding`, or `resolves` on mappings at acceptance) |
| Target context model | draft → proposed → accepted (a new change brings it back to draft with version+1) | `accept_model.py` after human approval |
| Column mapping | proposed → accepted (follows context acceptance) | `accept_model.py` |
| REQ | captured → analysed → designed → accepted → implemented (or superseded/rejected) | `memory_record.py status` |
| ADR | proposed → accepted / superseded / rejected | `memory_record.py status` |

## 3. File formats

### catalog.json
```json
{"schema_version":"1.0","engine":"postgresql","generated_at":"...",
 "tables":{"public.cust_mst":{
   "schema":"public","name":"cust_mst","kind":"table","comment":null,"row_count":120000,
   "columns":[{"name":"cust_id","ordinal":1,"data_type":"integer","nullable":false,"default":null,
               "is_pk":true,"is_unique":false,"comment":null,"max_length":null,"precision":null,"scale":null}],
   "primary_key":["cust_id"],"unique_constraints":[["email"]],
   "foreign_keys":[{"name":"fk_x","columns":["region_cd"],"ref_table":"public.region","ref_columns":["region_cd"]}],
   "indexes":[{"name":"ix","columns":["email"],"unique":true}]}}}
```
Keys are always lower-case `schema.table`. Column references everywhere are `schema.table.column`.

### relationships.json
`{"relationships":[{"table","columns","ref_table","ref_columns","source":"declared|inferred","confidence":0-1,"reason","status":"confirmed|inferred|rejected"}]}`
Re-running analysis keeps the human-set `status` of existing inferred entries.

### findings.json
`{"generated_at","rules_version","summary":{...},"findings":[{"id":"F-0001","rule":"LA-KEY-001","severity":"critical|high|medium|low|info","category","object":"schema.table[.column]","message","evidence","recommendation","status":"open"}],"table_scores":{"schema.table":0-100},"pii_inventory":[{"ref","class","reason"}]}`
When re-analysing, `analyze_schema.py` keeps `status` and `note` from the previous file, matched on rule+object.

### domains.json
`{"method","generated_at","domains":[{"name","status":"candidate|confirmed","description","tables":[...],"shared_tables":[...],"notes"}],"hubs":[...],"cross_domain_edges":[{"from","to","count"}]}`
`confirmed_by` records the reviewer. A legacy table belongs to exactly one domain's `tables`. Hub or reference tables used by many domains go in one domain's `tables` and in other domains' `shared_tables`.

### target/contexts/<ctx>/model.json
See `domain-modernization/references/target-model-format.md` for the full format. In summary: `context, schema, description, version, status, accepted_version, legacy_domains[], requirements[], tables[], enums[], external_refs[]`. After acceptance it also carries `approved_by` (display string) and `approvals[]` (`{"name", "role", "at"}` per approver).

### glossary.json
`{"terms":{"cust":{"expansion":"customer","uses":19,"status":"suggested|confirmed|unknown"}}}`. `model_lint` warns when target names use a legacy abbreviation.

### sme_questions.json
`{"questions": [{"id": "SQ-0001", "kind": "relationship|finding|term|global", "ref": "...", "tables": ["public.cust_mst"], "domain": "customer", "question": "...", "status": "open|answered|waived|resolved-by-review", "answer": "...", "answered_by": "Name (role)", "adr": "ADR-0004", "review_by": "2027-03-01", "reviews": [{"at", "by", "note", "previous_review_by"}], "superseded_waiver": {"adr", "review_by", "waived_by", "waived_at"}}]}`. Written by `build_report.py` (ids stay stable across rebuilds, answers are kept); answered with `review.py sme`. A question with no `tables` applies to every context. `accept_model.py` blocks a context while any question on its legacy tables is `open`, or `waived` under an ADR that is not accepted, or `waived` past its `review_by` date. `memory_status.py` lists every waiver with the accepted contexts that rely on it; `memory_validate.py` reports an overdue waiver as an error, and a waiver ADR still in force after the business answered (`superseded_waiver`) as a warning. Accepted models record `accepted_with_waivers[]`.

### mapping/<ctx>.json
```json
{"context":"billing",
 "table_mappings":[{"target":"billing.invoice","sources":["public.inv_hdr"],"grain":"one row per inv_hdr",
                     "filter":"inv_hdr.del_flg <> 'Y'","join":null,"notes":""}],
 "column_mappings":[{"target":"billing.invoice.invoice_number","sources":["public.inv_hdr.inv_no"],
                     "rule":"direct|transform|lookup|derived|split|merge|generated|constant|new",
                     "transform":"trim(inv_hdr.inv_no)","requirements":["REQ-0002"],"status":"proposed","notes":""}],
 "retired":[{"source":"public.inv_hdr.fax_no","reason":"no business use; confirmed by product owner","decision":"ADR-0004"},
            {"source":"public.inv_hdr_bak.*","reason":"backup copy of inv_hdr"}]}
```
- Use `rule:new` for target columns with no legacy source (new requirement data).
- Use `generated` for identity, uuid and audit columns.
- Any table or column mapping may carry `"resolves": ["F-0012"]`. Acceptance marks those legacy findings `resolved-in-target`.

### requirements / decisions index.json
`{"items":[{"id","title","status","source","contexts":[],"related":[],"file","created_at","history":[{"at","status","note"}]}]}`

## 4. Rules
1. **Legacy is the baseline, not the design.** Every target table must state its legacy sources in `table_mappings`, or say it is new. Every legacy column must eventually be mapped or retired with a reason. `coverage` measures this.
2. **Immutable history.** Do not edit snapshots, applied Flyway migrations, journal lines, or REQ/ADR ids. To change something, create a new version or a new ADR that supersedes the old one.
3. **One owner per table.** A target table belongs to exactly one context, and each context has its own schema. Other contexts refer to it by id only (`external_refs`), with no cross-schema foreign keys unless an ADR allows one.
4. **Scripts write the structured files.** Claude edits `model.json`, `mapping/*.json`, `domains.json` (names, descriptions, status), REQ/ADR bodies and `design.md`. Everything else goes through the scripts, so counters, journal and timestamps stay consistent.
5. **Small context reads.** Load memory through `memory_status.py` and `memory_query.py`. Do not cat `catalog.json` for large schemas.
6. **Validate before you finish.** Run `memory_validate.py`, which must report 0 errors.

## 5. Team and git workflow
- Use one branch per requirement (or a small batch of requirements). The PR contains the `.dbmod/` changes plus the generated Flyway and data-migration files, and is reviewed together.
- Merge conflicts are rare because files are split per context. If `manifest.json` counters conflict, keep the higher number, re-run `memory_validate.py`, and renumber the branch's new REQ/ADR ids if they clash.
- CI: `python <skills>/schema-memory/scripts/memory_validate.py --root . --strict`.
